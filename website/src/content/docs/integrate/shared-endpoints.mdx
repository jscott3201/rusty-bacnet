[Build and integrate](/rusty-bacnet/integrate/overview/) / Shared endpoints

Use an endpoint when one local device needs to initiate requests and serve them through the same transport. Its server role is the full server, read-only unless you say who may write. Standalone `BACnetClient` and `BACnetServer` remain public APIs.

## One session owns the connection

Rust's `EndpointSession` owns transport startup, ingress and shared outbound coordination. Choose `ClientOnly`, `ServerOnly` or `Both` before startup. The session's client and server use that owner and cannot independently restart its transport.

This complete B/IP program uses synthetic Device instance `1001` and vendor identifier `42`, creates both roles on an ephemeral port, and waits for Enter or stdin EOF before explicitly stopping the owner. It demonstrates startup, role availability and socket cleanup; it does **not** exercise a BACnet request/reply, discovery, a property write or Audit reporting.

The announced interface and configured broadcast destination are `127.0.0.1`. The default B/IP OS socket still binds wildcard (`0.0.0.0`), so this is **not a loopback-confined listener**. Run this synthetic example on an appropriate test machine; setting the announced interface does not change that bind behavior.

### Run and observe the owner

From the directory containing `Cargo.toml`, run:

```sh
cargo run
```

The first line contains the actual nonzero port assigned by the OS. Press Enter to stop. Redirected stdin EOF also stops the program. A successful run has this shape, using the same assigned port in both address lines:

```text
Started endpoint: 127.0.0.1:<assigned-port>
Roles: client=true server=true
Press Enter to stop (or send EOF).
Stopped: address=None client=false server=false
Rebound endpoint: 127.0.0.1:<assigned-port>; owner running=false
```

The role and address observations come from the session APIs. After awaited stop, the program checks the released port by binding a temporary UDP socket and observes the still-live owner again. It then drops that temporary socket. Printing a start address alone does not establish stop or role availability, and role availability does not establish requester/server traffic. A failure exits unsuccessfully; reporting and stdin errors after startup pass through the awaited-stop path.

CI compiles the exact source displayed here in the workspace and runs it through these lifecycle checks in the `shared_endpoint` integration tests. At each release, the release checklist also builds it with the displayed manifest outside the workspace, against the published crates. Neither establishes the release's minimum compiler, hardware behavior or protocol-service interoperability.

The declared Network Port in the program is not automatically registered. Explicit registration is a separate [receiving-port contract](/rusty-bacnet/integrate/network-ports/). A successful start exposes the actual B/IP address, including the ephemeral port; after stop it is unavailable.

For SC, `ScEndpointBuilder` composes a caller-dialed `TlsWebSocket` with `build_hub_session` under the `sc-tls` feature. For MS/TP, `MstpEndpointBuilder` owns one serial link. Python exposes `BipEndpoint`, `ScEndpoint` and `MstpEndpoint`, with `async with endpoint`, `await endpoint.client()`, a `BACnetClient` on the endpoint's one address with every call the standalone client has, and `await endpoint.server()`, the `BACnetServer` the endpoint's session runs there. As a Rust session with a server role does, a Python endpoint runs that full server: it answers discovery and every service a standalone server executes, and lists them in its Device. Without a `mutation_policy` it is read-only, denying every write, create and delete, so an endpoint nobody gave a policy is never writable by a peer; given one (`"permissive"`, `"deny_all"` or a callable), it is the server `BACnetServer(mutation_policy=...)` is, but for time synchronization, which an endpoint ignores until `time_sync_policy` turns it on. The application changes its objects through that server, whose COV and event notifications follow as on a standalone one. Its builders cover Analog and Binary Inputs and Values, Groups and Audit Reporters; other object types need a standalone `BACnetServer` for now.

B/IPv6 has no endpoint builder, as it has no server builder. In Rust, compose an `EndpointSession` over a `Bip6Transport` (the `bacnet-transport/ipv6` feature) and declare its Network Port with `DeviceIdentity::with_bip6_port`. Build the transport with `Some(instance)` of the Device the session serves: that instance is the port's VMAC, and a registered B/IPv6 port refuses to start with another instance or a random VMAC. Python has no B/IPv6 endpoint, and Ethernet has none in either language; use their standalone owners.

## Check requester and server scope separately

| Role | Contract |
|---|---|
| Client | Rust `session.client()` or Python `await endpoint.client()`: a `BACnetClient` with every call the standalone client has, one at a time, on a running session of any role |
| Client beside a server | Answers only the COV notifications of its own subscriptions; the server answers every other request |
| Server role | The full server's service set, on the session's Device identity, which a Rust session with a server role must have |
| Default server | Read-only: reads, Who-Is, Who-Has and COV subscriptions answered; writes, creates and deletes denied; ReinitializeDevice and DeviceCommunicationControl refused; time synchronization ignored |
| Server with a policy | Rust `with_server(builder)` or Python `mutation_policy`: that policy, as on a standalone server |

The Device lists the services the node executes: the full server's, and on a session of both roles the client's COV notification, I-Am and I-Have services beside them. Earlier releases ran a narrow responder in the Rust session instead, which answered ReadProperty alone unless opted in, and a narrow requester limited to unsegmented reads and direct B/IP writes.

A write takes no commandability declaration: one sent with a priority is a command at that priority, and one without names none. Neither is permission to write the remote property. For a first integration, exercise reads before enabling mutations. Consult <a href={`${repository}/blob/v${release}/docs/request-admission.md`}>request admission limits</a> for the shared budgets.

## Add source READ or WRITE Audit reporting deliberately

The optional Rust source Reporter profile belongs to this session and currently covers **direct IPv4 B/IP**. Configure it before startup:

1. Put a concrete built-in Device and the selected Audit Reporter in the database. If it holds several Devices, the lowest instance is the local one (<a href={`${repository}/blob/v${release}/docs/rust-api.md#databases-with-several-devices`}>details</a>).
2. Provision the Device's typed Audit recipient. A Device recipient needs an immutable `source_audit_device_binding`; a direct Address recipient needs none.
3. Set the Reporter's audit level and READ/WRITE operation policy. `Monitored_Objects` must be absent, including no empty or NULL-only list.
4. Select `with_source_audit_reporter`. A `Both` session needs a server whose policy decides mutations, so that no peer rewrites the recipient unasked: the read-only default does.

The <a href={`${repository}/blob/v${release}/docs/rust-api.md#bounded-endpoint-source-read-reporting`}>canonical source Reporter example</a> supplies the exact setup. Python endpoints select one with `source_audit_reporter`, beside a server whose `mutation_policy` decides writes: the read-only default, `"deny_all"` or a callable.


READ reporting covers RP, ReadRange and RPM. Records retain attempted identities and outcomes; returned values remain caller-only. An RPM operation can produce a separate record for each eligible occurrence. WRITE reporting records eligible attempts across retries, with a complete Target_Value only when its encoding fits 0–32 bytes. It never invents remote Current_Value, target timestamp or proof that a write executed. Notification delivery failure does not replace the request's result.

This source profile is separate from the full server's <a href={`${repository}/blob/v${release}/docs/target-audit-reporters.md`}>target Reporter ownership</a>, <a href={`${repository}/blob/v${release}/docs/device-audit-recipient.md`}>Device recipient</a> and Audit Log forwarding contracts.

## Close the owner, including after cancellation

In Rust, await `session.stop()`; in Python, await `close()` or leave the async context. A client kept past the stop does not keep a closed session usable: each of its calls fails. Stop owns admitted work and transport cleanup; dropping a caller's request is not a substitute for stopping the endpoint.

Eligible source-reported requests retain terminal observation after caller cancellation. Other caller-owned requests can cancel queued sends, but an already attempted send may have reached its peer. Cancellation never proves that a remote write did not execute.

Python startup and close serialize through the native lifecycle owner. If startup cancellation races publication, explicitly await close. A canceled admitted close waiter leaves cleanup owned; another awaited close joins it. Successful start consumes registrations, so restart does not replay them. See the <a href={`${repository}/blob/v${release}/docs/python-api.md#endpoint-lifecycle-and-cancellation`}>full lifecycle contract</a> for startup rollback boundaries.
