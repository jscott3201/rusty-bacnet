[Build and integrate](/rusty-bacnet/integrate/overview/) / Route between networks

A BACnet router joins two or more networks, each with its own network number, and passes messages between them (Clause 6). `BACnetRouter` is that router in Rust: each port is one transport on one network, such as two BACnet/IP subnets, or a BACnet/IP network and an MS/TP trunk. It forwards requests and replies, keeps a routing table, and answers the network-layer messages other nodes use to find it. Clients and servers on the attached networks need nothing special to talk through it. Python has a B/IP router too.

The page describes **v{release}**.

## Give each port a network number

`BACnetRouter::start(ports, options)` takes a list of `RouterPort::new(transport, network_number)` ports and starts every transport:

- A network number is 1 to 65534, and each port needs a different one. Every router on a network must use the same number for it.
- All ports share one transport type. `RouterPort`'s transport type defaults to `AnyTransport`, so a router that mixes link types wraps each transport in `AnyTransport` and writes `RouterPort` alone.
- `RouterOptions::new()` is the plain router. The options below turn on more.
- `RouterPort::new(transport, network_number).isolated(true)` marks a port as isolated. The router carries nothing between two isolated ports and hides each from the other, while both still reach the ordinary ports: several BACnet/SC hubs can share one B/IP network without reaching each other. It limits transit only, by design: it is not a trust level for a port, and a reject or a routing-table update from an isolated port can still change a route through an ordinary port. `next_hop_rejects()` and the control policy, both below, are the controls for those. The rustdoc of `RouterPort::isolated` says what differs on the wire.

`start` returns a `StartedRouter` with the router and a receiver, `apdus`, for messages addressed to the router itself, which an application on the router may answer. `router.table()` borrows the routing table: read or change what you need, then drop it before the next `.await`. `router.counters()` reports what the router dropped or refused, and `router.ports()` lists each port's network number and actual MAC.

The router's own application can be a client or a server too. `StartedRouter::into_application_port()` makes it a transport for a `BACnetClient`, and `into_application_ports()` splits it between a `BACnetServer` and a client. `BACnetRouter::originate` sends a global broadcast from the router's own application, such as a Who-Is for every network, on every port.

## Find routers and the devices behind them

A node finds the router to a network with Who-Is-Router-To-Network, and each router answers with I-Am-Router-To-Network and the networks it reaches (Clauses 6.4.1 and 6.4.2):

- Rust's `client.discover_routers(Some(network), wait)` and Python's `await client.discover_routers(network, wait=...)` broadcast the question and return each router that answered, with the networks it lists. Leave the network out to hear every router. To ask one router alone, use Rust's `client.discover_routers_directed(&router_mac, network, wait)`, Python's `router=` keyword or the CLI's `whois-router --router ADDRESS`. The router answers with a local broadcast, so a B/IP router on another IP subnet is heard only when a BBMD forwards its answer here, as a peer or by foreign-device registration.
- A global Who-Is reaches every network, since routers carry it on, and each answer records the network the device is on. Rust's low-level `client.who_is(Broadcast::Global, range)` sends one; Python's `who_is()` and `discover()` and the CLI's `discover` stay on the client's own network unless told otherwise, with `scope="global"` (or a network number) and `--global` (or `--dnet`). Then Rust's `client.resolve_device(instance)` gives the station behind the router that answered, and a read to it goes through that router, as Python's `read_property_from_device(instance, ...)` does.
- In Rust, every typed call takes a `Station`: `client.read_property(&Station::routed(&router_mac, network, &device_mac), ...)` addresses a device on another network directly, when you already know the router's address and the device's address on its own network. A `BACnetAddress` of the network and the device's MAC goes through the router the discovery table holds for it instead. With no router known yet, `Station::routed_via_local_broadcast(network, &device_mac)` sends the request by one broadcast on the link that names the device, and the router to that network passes it on. A router address that is the link's broadcast or a group address, or a device address that is its network's broadcast, is refused before anything is sent; a device that is one station at such an address (station 255 on an ARCNET network, or a gateway's two-octet virtual station) is marked with `.one_station()`, or Python's `RoutedTarget(..., one_station=True)`.

From the CLI, `whois-router` lists the routers and the networks they reach, and `discover --dnet` asks one network for its devices. Replace the network number and device instance with your site's:

```sh
bacnet whois-router
bacnet whois-router --dnet 5 --wait 5
bacnet discover --dnet 5 --wait 3
bacnet read 5:1005 ai:1 pv
```

A routed target is `NETWORK:INSTANCE`, as `5:1005` above, or `NETWORK:0xMAC` for a station by its address on that network, such as `2:0x05` for MS/TP station 5 on network 2. A station whose MAC looks like a broadcast or group address but is one station is written `5:0xFF:one-station` (ARCNET station 255) or `9:0x0012:one-station` (a gateway's two-octet virtual station); the suffix is refused anywhere it lifts nothing. The CLI asks that network for the device and sends the request through the router that answers. `read`, `readm`, `read-range`, `write`, `writem`, `subscribe`, `alarms`, `alarm-summary`, `enrollment-summary`, `ack-alarm`, `create-object`, `delete-object`, `control`, `reinit`, `time-sync`, `file-read` and `file-write` take routed targets, with the same write guards as a local target. The B/IP management commands `bdt`, `fdt`, `register` and `unregister` address local peers and refuse them.

## Router options worth knowing

Each option is a `RouterOptions` method:

- `control_policy(ControlPolicy::Hardened)` with `control_authorizer(..)` decides which peers may change routes with network-layer messages. Without them, any peer's routing messages are applied. The same gate decides whether the router answers a routing-table query that arrives from another network, which it does by default: the answer is the whole table, sent toward a source the query only claims. See <a href={`${repository}/blob/v${release}/docs/rust-api.md#who-may-change-routes-518`}>who may change routes</a>.
- `congestion(Congestion::DEFAULT)` tells the other networks, with Router-Busy-To-Network, when a port's send queue stays full, and with Router-Available-To-Network when it drains.
- `duplicates(Duplicates::DEFAULT)` drops a global broadcast the router saw within the last second. It is meant for a site whose routers form a loop, which the standard doesn't allow but a misconfigured site can have. The standard defines no such suppression, and a sender's own identical retry within that second is dropped too. It also covers three messages the router passes on without a hop count, so that nothing else stops them around a loop: I-Am-Router-To-Network, and Router-Busy-To-Network or Router-Available-To-Network from one sender.
- `next_hop_rejects()` lets a Reject-Message-To-Network change a learned route only when it comes from that route's next router.
- `remote_table_updates()` takes routing-table updates (Initialize-Routing-Table with a port count other than zero) that arrive from another network. Without it the router drops them, whatever the control policy, and applies only updates from its own networks: one update can remove or redirect any learned route. Table queries are answered either way.
- `track_admission()` gives the local receiver queue counters and a per-source quota.

## Know the limits

| Limit | Value |
|---|---|
| Ports | 1 to 255 |
| Routes, direct ones included | 256 |
| Sends queued per port | 256 |

At the route limit, the router stops learning new routes. See <a href={`${repository}/blob/v${release}/docs/rust-api.md#bacnet-network`}>the network layer</a> for how routes are learned and aged.

## Stop the router

`router.stop().await` returns `Result<(), RouterStopError>`. It waits for every transport to stop, and only `Ok` means every port's socket is closed; `failures()` lists what failed. Calling it again returns the same result. Queued local messages stay readable from `apdus`.

## A router in Python

`BACnetRouter([BipRouterPort(network, interface=..., port=..., broadcast_address=...), ...])` owns a B/IP router with 1 to 255 ports. The `bbmd=Bbmd(...)` and `foreign_device=ForeignDevice(...)` options the client and server take work on a port too. Start it with `async with` or `await router.start()`; `await router.ports()` gives each port's actual address, and `await router.routes()` copies the routing table. A successful `await router.close()`, or leaving the context, waits until every port's socket is closed.

It routes between B/IP networks only. Of the options above it takes three, as keywords: `remote_table_updates=True`, `next_hop_rejects=True` and `control_policy="hardened"`, which with no authorizer in Python denies every protected routing message: the router learns no routes, so only its directly attached networks are reachable, and it refuses `remote_table_updates` or `next_hop_rejects` beside it, since neither could ever apply. `await router.counters()` returns the router's counts by name, the control decisions among them. A port does take `isolated=True`, which keeps it apart from the router's other isolated ports as `RouterPort::isolated` does in Rust, with the same limit: it is a rule about transit, not a trust level for the port.

The router's own application entity can host Python stacks too. Build the router with `application="client"` for one `BACnetClient`, or `application="client_and_server"` for a `BACnetClient` and a `BACnetServer`, and build each stack with `transport="router", router=router`. Each takes its share when it starts, once per router start. The client reaches every device through the router's table, so it names each one by its network. The application is on each of the router's networks, so a plain `discover()` asks every one of them and no network beyond; `scope="global"` or a network number widen or narrow it. Then use the `_from_device` methods. The server answers at the router's address on each network. A local broadcast from either stack, such as the server's I-Am or an event notification to a local-broadcast recipient, goes to each of the router's networks, isolated ports included; a recipient that names one network's number reaches that network alone. Closing the router ends both shares, and their requests then fail at once.

## Example: two B/IP networks on one host

These programs start a router with ports on networks 1 and 5, both on 127.0.0.1, a device (instance 1005) on network 5 and a client on network 1. The client finds the router, finds the device with a Who-Is to network 5, and reads its Analog Input through the router. Then everything stops.

All three share 127.0.0.1, so a B/IP broadcast from one would reach none of the others. Each router port is therefore a BBMD, and the device and the client register with it as foreign devices, which sends their broadcasts through it. On a real site each port would sit on its own subnet and plain broadcasts would do.
