# Docker BACnet/SC pair — Secure Docker (recommended)

The paired `bacnet-sc-hub` and `bacnet-device --transport=sc` topology uses
**mutual TLS 1.3**, with caller-provided PEM credentials and explicit device identity.
The hub requires and verifies client certificates. The device validates the hub
certificate against its explicit CA and the URL's hostname or IP address, and
configures a matching operational certificate/key to offer for client authentication.
This is an immediate compatibility change: `--self-signed` and `--sc-no-verify`
are rejected with migration advice before file or network I/O. No credentials
are generated by either binary or by Compose. There is no unsafe or system-root
fallback. Help/version and BIP/foreign-device operation need no SC files.

## Provide credentials

Use your site's credential process for real deployments. The example expects:

```text
sc-certs/
  ca.pem
  hub/cert.pem
  hub/key.pem
  device/cert.pem
  device/key.pem
```

`SC_CERT_DIR` defaults to `./sc-certs`, relative to this Compose file. For a
custom directory, use an absolute path **outside the checkout**. The CA file is
the explicitly trusted issuer bundle. Operational chains are leaf first; keys
must match, be usable unencrypted PEM, and be kept private (mode `0600`).
The hub certificate must cover `172.20.3.2` (the URL used by `sc-server`) and
`sc-hub` if using the Compose DNS name. The device certificate needs clientAuth;
the hub certificate needs serverAuth. Each endpoint gets only its own key.
The signing CA private key belongs in a separate private host location: **never
mount it, copy it into the build context, or put it in the credential directory**.

Compose uses six endpoint-specific read-only **file** mounts, not a directory
mount. `bind.create_host_path: false` requests rejection of missing sources.
Some Compose versions have had missing-path bugs; a missing path must still
fail closed at mount or PEM loading, never start an unauthenticated endpoint.
Do not rely on all versions leaving the host untouched; inspect unexpected
directories rather than placing credentials in them blindly. No SELinux host
relabel is requested. On Docker Desktop, host paths must be accessible to the
Desktop file-sharing bridge. Do not loosen key permissions to work around it.

### Manual development-only OpenSSL recipe

This is a **manual local development recipe**, not automatic provisioning or a
production PKI/renewal tool. Requires OpenSSL 3.x, a trusted host, and correct
clocks. Run from `examples/docker`. Choose two **new, nonexistent** directories;
the parent directories must already exist and be private/trusted. Never rerun
this to replace an existing CA. No host trust store is modified.

```sh
# Example inputs; choose your own private host paths before running the block.
export SC_CERT_DIR="$PWD/sc-certs"
export SC_CA_PRIVATE_DIR="$HOME/private-sc-development-ca"
```

```sh
(
  set -eu
  umask 077
  : "${SC_CERT_DIR:?Set a new credential directory}"
  : "${SC_CA_PRIVATE_DIR:?Set a separate new private CA directory}"
  if test -e "$SC_CERT_DIR" || test -L "$SC_CERT_DIR"; then exit 1; fi
  if test -e "$SC_CA_PRIVATE_DIR" || test -L "$SC_CA_PRIVATE_DIR"; then exit 1; fi
  # No -p: refuse existing directories; no existing CA or key is overwritten.
  mkdir "$SC_CA_PRIVATE_DIR"
  mkdir "$SC_CERT_DIR"
  mkdir "$SC_CERT_DIR/hub" "$SC_CERT_DIR/device"
  openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:P-256 -noenc \
    -subj '/CN=Local SC Development CA' -days 7 \
    -addext 'basicConstraints=critical,CA:TRUE,pathlen:0' \
    -addext 'keyUsage=critical,keyCertSign,cRLSign' \
    -keyout "$SC_CA_PRIVATE_DIR/ca.key" -out "$SC_CERT_DIR/ca.pem"
  openssl req -new -x509 -newkey ec -pkeyopt ec_paramgen_curve:P-256 -noenc \
    -subj '/CN=sc-hub' -days 2 \
    -CA "$SC_CERT_DIR/ca.pem" -CAkey "$SC_CA_PRIVATE_DIR/ca.key" \
    -addext 'basicConstraints=critical,CA:FALSE' \
    -addext 'keyUsage=critical,digitalSignature' \
    -addext 'extendedKeyUsage=serverAuth' \
    -addext 'subjectAltName=IP:172.20.3.2,DNS:sc-hub,DNS:localhost,IP:127.0.0.1' \
    -keyout "$SC_CERT_DIR/hub/key.pem" -out "$SC_CERT_DIR/hub/cert.pem"
  openssl req -new -x509 -newkey ec -pkeyopt ec_paramgen_curve:P-256 -noenc \
    -subj '/CN=sc-device-5000' -days 2 \
    -CA "$SC_CERT_DIR/ca.pem" -CAkey "$SC_CA_PRIVATE_DIR/ca.key" \
    -addext 'basicConstraints=critical,CA:FALSE' \
    -addext 'keyUsage=critical,digitalSignature' \
    -addext 'extendedKeyUsage=clientAuth' \
    -keyout "$SC_CERT_DIR/device/key.pem" -out "$SC_CERT_DIR/device/cert.pem"
  chmod 600 "$SC_CA_PRIVATE_DIR/ca.key" "$SC_CERT_DIR/hub/key.pem" "$SC_CERT_DIR/device/key.pem"
  chmod 644 "$SC_CERT_DIR/ca.pem" "$SC_CERT_DIR/hub/cert.pem" "$SC_CERT_DIR/device/cert.pem"
  openssl verify -CAfile "$SC_CERT_DIR/ca.pem" -purpose sslserver \
    -verify_ip 172.20.3.2 "$SC_CERT_DIR/hub/cert.pem"
  openssl verify -CAfile "$SC_CERT_DIR/ca.pem" -purpose sslserver \
    -verify_hostname sc-hub "$SC_CERT_DIR/hub/cert.pem"
  openssl verify -CAfile "$SC_CERT_DIR/ca.pem" -purpose sslclient "$SC_CERT_DIR/device/cert.pem"
  # These opposite-purpose checks MUST fail.
  if openssl verify -CAfile "$SC_CERT_DIR/ca.pem" -purpose sslclient "$SC_CERT_DIR/hub/cert.pem"; then exit 1; fi
  if openssl verify -CAfile "$SC_CERT_DIR/ca.pem" -purpose sslserver "$SC_CERT_DIR/device/cert.pem"; then exit 1; fi
)
```

Keep the CA key private for review/renewal, or destroy it deliberately when the
short-lived development site is no longer needed. Do not print private keys.
`.gitignore` and `.dockerignore` exclude the default credential directory and
PEM/key build products, but cannot recognize arbitrary renamed secrets: custom
credential/CA directories must stay outside the checkout.

## Start only the SC pair

From this directory, choose a project name that does not collide with another
deployment. Check that the example's `172.20.3.0/24` network does not overlap any
existing Docker network. Do not remove another project's network to make room.

```sh
export COMPOSE_PROJECT_NAME=rusty-sc-mtls-local
docker compose config
docker compose build sc-hub sc-server
docker compose up -d sc-hub sc-server
docker compose logs sc-hub sc-server
```

No host ports are published. Hub health checks establish **listener readiness
only**, not mutual authentication or application correctness. The device then
performs TLS, WebSocket and SC Connect handshakes. Verify a real BACnet
ReadProperty with an independently credentialed peer on the SC network; logs
alone are not that verification. All non-SC services/networks retain their
existing configuration. Rendering `docker compose config`, building images, or
starting only non-SC services does not require globally supplied SC variables.

### Hub identity migration

The standalone hub now requires `--device-uuid`: exactly 32 ASCII hex digits
without separators, nonzero. Missing/empty/malformed/zero UUIDs fail before
credential-file I/O or bind. Credential-presence diagnostics still run first;
`--self-signed`, help and version retain their earlier behavior. Optional `--vmac`
accepts 12 ASCII hex digits and defaults to the existing `000000000001`; all-zero
and all-ff values are rejected. No UUID is generated or hardcoded in the binary.

Compose explicitly supplies **stable TEST-ONLY fixtures**: hub-hosting device UUID
`9a21f1641a15454d9ed7e3a2710d7001`, hub VMAC `000000000001`, and the unchanged
server UUID `00000000000000000000000000001388`/VMAC `020000001388`. Replace demo
UUIDs with your own unique identities before real deployment (for example in your
explicit Compose command override). No extra environment variable is required for
unrelated non-SC Compose commands. Reuse exactly the same provisioned UUID across
restarts/recreation and credential rotation for each device's lifetime; the caller
owns predeployment generation and durable storage (base 2020 AB.1.5.3).

Connect-Accept advertises the hosting port VMAC and hosting device UUID (AB.2.11,
AB.6). They are not inferred from certificates or Device instance numbers. Give
each distinct device a unique UUID; same-UUID peer replacement remains intentional.
The local hub rejects only zero UUID/reserved VMAC, not UUID version/variant or
other VMAC bit patterns. No storage backend, change detection, certificate binding
or full #517 closure is provided. The built-in Rust TLS driver still requires
`ScNodeTlsConfig`; TLS and credential-mount policy are unchanged.

## Rotation and teardown

Replace expired credentials through your site's process, verify CA/chain,
purpose, names and key match, and recreate both SC services:

```sh
docker compose up -d --force-recreate sc-hub sc-server
# When finished with this project only:
docker compose down
```

**A restart is not sufficient after atomic file replacement:** file bind mounts
can remain pinned to the old inode. Recreation refreshes mounts and TLS config;
there is no automatic reload, renewal, or CA creation. Plan trust overlap and
rotation of other site nodes separately. Do not regenerate a CA on every `up`.

TLS 1.3-only and rustls server-name verification are local deployment policy.
The mTLS claim applies to this paired topology, whose hub enforces client
certificate verification. Configuring the device's credentials does not attest
that an arbitrary remote hub requests or verifies its client certificate.
This example does not certify the full BACnet/SC profile, revocation handling,
direct-issuer policy, certificate-to-VMAC/UUID authorization, or physical-device
interoperability (#513 remains partial). All public Rust hub startup now requires
`ScHubTlsConfig`; this example already uses its compatible alias, without a change
to provisioning or runtime behavior. Server-auth-only SC benchmark targets are
retired; historical results remain. The device and smoke peer now use the shared
strict local `ScNodeTlsConfig` factory without provisioning or CLI changes.
Normal TLS resumption is preserved and may not retransmit certificates; a trusted
server without CertificateRequest can complete without receiving node credentials.
The paired strict hub requests and verifies credentials, but the node factory alone
does not enforce that remote behavior or establish full-profile conformance.
